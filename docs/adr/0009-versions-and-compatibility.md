# 0009 内核与客户端分开的版本号，兼容性看协议版本

状态：已采纳

## 决定

- 两套版本号，同一个仓库：
  - **内核版本**是根 `Cargo.toml` 的 `[workspace.package] version`，所有 crate 继承它，`eddy-server` 和 `eddy-cli` 也用这个版本。标签 `core-vX.Y.Z`，变更记在根目录 `CHANGELOG.md`（两份 changelog 都按 Keep a Changelog 1.1.0 的格式写）。
  - **客户端版本**是各平台应用自己的版本：Mac 应用在 `apple/project.yml` 的 `MARKETING_VERSION`（给人看）和 `CURRENT_PROJECT_VERSION`（每次发布加一）。标签 `mac-vX.Y.Z`（以后 `ios-v…`、`android-v…`），变更记在 `apple/CHANGELOG.md`。
  - 只改界面时只升客户端版本，内核版本不动；改了内核而界面没变时反过来。两边都用 `scripts/bump-version.sh core|mac X.Y.Z` 修改。
- 运行时两个版本都看得到：应用的 Settings → About 同时显示客户端版本和内核版本（带提交哈希）；`eddy-server --version`、`eddy-cli --version` 和 `/v1/info` 的 `version` 报内核版本。提交哈希由 `eddy-core/build.rs` 写入，Docker 构建通过 `EDDY_GIT_HASH` 传入。
- 两端能不能一起工作不看上面两个版本号，看三个各自独立的数：
  1. **同步协议版本** `eddy_sync::PROTOCOL_VERSION`。客户端每个请求带 `x-eddy-protocol`；服务端在 `/v1/info` 里报 `protocol` 和它还接受的最低版本 `min_protocol`。任何一方发现对方超出自己支持的范围就拒绝同步并明确提示该更新哪一边（服务端回 426，客户端报 `UpgradeRequired`），本地功能不受影响。
  2. **数据库结构版本**（`eddy-store` 的迁移数，存在 `PRAGMA user_version`）。只向前迁移；打开比自己新的数据库时直接拒绝并提示更新，绝不写入。
  3. **文档结构版本** `eddy_doc::SCHEMA_VERSION`，规则不变（见 [0003](0003-document-model-and-locator.md)）：版本不符的文档从原始内容重新生成。
- 什么时候升同步协议版本：新增实体、新增字段，或已有字段的含义变了——也就是旧的一方会读错或读不懂的时候。只加带默认值的可选信息（例如 `ServerInfo.video_capable`）不用升。升级时先更新服务端再更新各设备；`MIN_PROTOCOL` 只在确实要放弃旧版本时才提高。
- 读不懂的操作不会卡住同步，也不会丢：
  - 服务端收到解析不了的操作（来自更新的客户端）、取值不对的操作或时间戳超前太多的操作时，只拒绝这一条并在响应的 `rejected` 里说明原因，同一批里的其他操作照常生效。客户端把被拒的操作标成不再重传，数量显示在设置里；服务端的协议版本变了以后再重试一次。
  - 客户端拉到解析不了的操作（来自更新的服务端）时跳过并记下标记；这台设备的内核升级后从头再拉一遍日志，把当时跳过的补上（已有的操作按 `op_id` 忽略）。

## 理由

- 客户端和内核的发布节奏不同：界面调整很频繁而且不影响数据，内核的变化则关系到数据格式和多端兼容。共用一个版本号要么让界面小改也变成"内核升级"，要么让版本号说明不了任何事。
- 应用静态链接同一提交的内核，两者不存在运行时的版本错配，所以不需要应用声明"依赖内核某版本"的机制，更不需要单独存放预编译内核的发布流程；真正会错配的是不同设备和服务端之间，以及新旧程序和同一份数据之间，这正是上面三个数管的事。
- 服务端几乎全部逻辑都在内核里，单独给它一个版本号没有信息量。
- 逐条拒绝而不是整批失败，是因为客户端先推后拉：一条永远过不去的操作会连带挡住这台设备的全部同步，而这类操作恰恰最可能出现在版本交替的时候。

## 后果

- 发布内核或客户端各自独立：`scripts/bump-version.sh` 改版本号并把 changelog 的 `Unreleased` 定成这个版本，合并到 `main` 后打对应标签；推送标签由 `.github/workflows/release.yml` 完成发布（内核发服务端镜像，Mac 发应用包）。
- 旧版本程序遇到新数据时会停在一条明确的提示上，而不是带着读不懂的数据继续跑。
- 协议版本 1 的客户端（没有协议头）连不上现在的服务端；在这次改动之前没有对外发布过，不保留兼容。
