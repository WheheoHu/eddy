# 0010 服务端离线时，设备直接从 FreshRSS 取新文章

状态：已采纳（修订 [0002](0002-local-first-optional-server.md) 中"连接服务端后 FreshRSS 账号只在服务端"的做法）

## 决定

- 服务端不在线时，客户端除了取新内容以外的功能本来就不依赖它；这条决定把"取新文章"也补上，并把"不依赖"落实成可验证的行为：
  - 阅读、已读/星标、保存网页、导入、标签、系列、设置、本地搜索、AI 都只走本地。每个本地修改照旧先写操作日志，然后自己排队上传：失败后退避重试，实时通道重新连上时立即补传，不需要等用户点刷新。
  - 引擎状态带上 `server_online`、`pending_uploads`、`rejected_uploads`；连不上服务端是一种明确的状态（`Offline`），界面据此显示"服务端离线、N 条改动待上传"，不当成错误弹出来。
  - 搜索和视频任务列表在服务端刚失败过的一小段时间内直接用本地结果，不再等一次超时；打开文章时从服务端取内容失败后继续尝试原网页和 FreshRSS。
- 连接服务端时，本机的 FreshRSS 账号和密码**保留**在本机（同时交给服务端）。服务端模式下刷新先走服务端；只有在连不上服务端时，才用本机账号直接向 FreshRSS 拉一次：
  - 只入库**新文章**和它们当时的已读/星标状态。
  - **不向 FreshRSS 写任何东西**，也不用 FreshRSS 的状态覆盖本机已有条目，不删除订阅源，不回溯历史。离线期间的已读/星标只进操作日志，等服务端回来由服务端写回 FreshRSS。
  - 条目 ID 由账号（地址 + 用户名）和上游 ID 推算，所以服务端恢复后发来的同一篇文章会合并到本机已有的那一条上，不会重复，也不会再次被当成新文章触发自动全文和 AI。
- 这要求本机账号和服务端管理的是同一个账号：配对时如果服务端已有账号且和本机的不同，配对在改动本机任何状态之前失败；之后在服务端模式下填写的 FreshRSS 账号也必须与服务端一致。
- 没有 FreshRSS 账号的设备（后来加入的设备）在服务端离线时照常工作，只是不会有新文章；可以在设置里填密码开启离线刷新。
- 断开服务端时，本机还有账号的话直接回到单机模式，尚未上传的已读/星标改为推给 FreshRSS。

## 理由

- 服务端是可选的，不该在连接之后变成单点：一台停掉的服务器不应该让阅读器看不到新文章。
- 保持"只有一方写 FreshRSS"是这套设计能不出冲突的前提。如果离线的设备也直接写 FreshRSS，同一个已读状态就会从两条路径到达，而 FreshRSS 没有时间戳可以比较先后。只读拉取避开了这个问题。
- 让密码留在设备上的代价是它多存了一份，但它本来就来自这台设备的钥匙串，也只存在钥匙串里。

## 后果

- 服务端离线期间，在别处（FreshRSS 网页、另一台设备）做的已读/星标要等服务端恢复后才会到达本机。
- 离线期间本机入库的新文章，其内容版本在服务端恢复后以服务端入库的版本为准。
- 设置页在服务端模式下也显示 FreshRSS 一节，说明本机是否保留了账号。
